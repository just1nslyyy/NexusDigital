NexusDigital — ТЗ и дорожная карта MVP
Версия: 0.1 — проект на согласование
Статус: черновик требований; разработка по этому документу ещё не начата
Продукт: магазин цифровых товаров с интерфейсом Telegram Mini App
1. Цель MVP
Создать минимальную, но целостно работающую версию NexusDigital, в которой пользователь может открыть магазин, найти цифровой товар, оформить заказ, оплатить его через один подключённый платёжный провайдер и безопасно получить свой экземпляр товара.

Главное техническое требование: один цифровой экземпляр нельзя выдать более чем одному успешно оплаченному заказу, даже при параллельных запросах, повторах webhook или временных сбоях.

MVP предназначен для проверки полного пользовательского сценария и технической основы. Он не означает автоматически готовность к большим промышленным нагрузкам.
2. Пользователи и роли
Покупатель
- Открывает приложение через Telegram.
- Просматривает каталог, ищет товары и открывает карточку товара.
- Видит цену и доступность товара.
- Создаёт заказ и проходит оплату.
- Просматривает свои заказы и получает купленный цифровой товар.
Администратор
- Входит в закрытую административную часть.
- Создаёт и редактирует товары.
- Добавляет цифровые экземпляры в склад.
- Просматривает заказы и статусы платежей.
- Может скрыть товар из каталога и отключить экземпляр, если он больше не должен продаваться.
Не входит в первую версию
- Самостоятельная регистрация продавцов и многопоставщицкая площадка.
- B2B-кабинеты, оптовые тарифы и расчёты с поставщиками.
- Внутренний кошелёк и хранение денежного баланса.
- Реферальная система, промокоды, сложная программа лояльности.
- Несколько платёжных провайдеров, мультивалютность и сложная налоговая логика.
- Нативные приложения iOS/Android вне Telegram Mini App.
3. Основные пользовательские сценарии
3.1 Просмотр каталога
1. Пользователь открывает Mini App.
2. Приложение загружает список опубликованных товаров из API.
3. Пользователь может искать товары по названию и фильтровать по категории.
4. Для каждой позиции показываются название, изображение при наличии, краткое описание, цена и состояние наличия.
5. Наличие, отображаемое в интерфейсе, является справочной информацией: при создании заказа сервер повторно проверяет остаток.
3.2 Покупка цифрового товара
1. Клиент отправляет запрос на создание заказа с уникальным ключом идемпотентности.
2. Сервер проверяет пользователя, товар, актуальную цену и наличие.
3. В короткой транзакции PostgreSQL выбирается свободный экземпляр и резервируется до заданного времени окончания.
4. В той же транзакции создаётся заказ со снимком цены и валюты на момент оформления.
5. Транзакция фиксируется; внешняя оплата выполняется уже после завершения транзакции, без удержания блокировки товара во время ожидания платёжного провайдера.
6. Пользователь оплачивает заказ через платёжного провайдера.
7. Backend проверяет подлинность webhook, идентификатор заказа, сумму и валюту. Повторные уведомления не должны повторно выполнять покупку.
8. Если оплата подтверждена и резерв всё ещё принадлежит этому заказу, экземпляр помечается проданным, заказ — оплаченным/выданным.
9. Покупатель может получить цифровой товар в защищённом разделе своих покупок. Telegram-уведомление — дополнительный канал, а не единственное место выдачи.
3.3 Истечение резерва и поздняя оплата
- Неоплаченный резерв истекает по заданному TTL; фоновая задача освобождает зарезервированный экземпляр и обновляет статус заказа.
- Если подтверждение оплаты приходит после истечения резерва, система не выдаёт автоматически экземпляр, который уже мог достаться другому покупателю. Заказ переводится в отдельное состояние для безопасного восстановления или возврата и отображается администратору.
- Система должна сохранять историю состояния, чтобы спорные случаи можно было расследовать.
3.4 Управление каталогом
1. Администратор создаёт товар с названием, описанием, категорией, ценой, валютой и состоянием публикации.
2. Администратор добавляет отдельные цифровые экземпляры или загружает их из CSV, если импорт будет включён в первую версию.
3. Чувствительное содержимое экземпляров нельзя отдавать в публичном API каталога или логировать в открытом виде.
4. Архивирование товара не удаляет связанные исторические заказы.
4. Функциональные требования
Каталог
- Список опубликованных товаров, карточка товара, поиск по названию.
- Фильтрация по категории — простая версия.
- Цена и валюта хранятся на сервере; клиент не может назначать стоимость покупки.
- Товар без доступных экземпляров нельзя купить.
Telegram-авторизация
- Backend проверяет исходный initData Telegram по официальному алгоритму с использованием секрета бота.
- Непроверенным полям со стороны frontend доверять нельзя.
- Проверяется свежесть auth_date в пределах настроенного допустимого интервала.
- После проверки backend выдаёт ограниченную по сроку пользовательскую сессию.
- Для локальной разработки допускается отдельный тестовый режим, который выключен по умолчанию и не может включаться в production случайно.
Заказы и резервы
- Заказ имеет уникальный публичный идентификатор и внутренний ID.
- Цена и валюта сохраняются в заказе в момент оформления.
- Состояния заказа: pending_payment, paid, fulfilled, expired, cancelled, payment_review, refund_pending, refunded, fulfillment_failed — окончательный набор может быть упрощён при проектировании, но переходы должны быть явными.
- Состояния цифрового экземпляра: available, reserved, sold, disabled.
- Резерв имеет время окончания.
- Создание заказа идемпотентно: одинаковый ключ запроса не создаёт несколько заказов для одной операции.
- Система использует транзакции PostgreSQL и блокировку строк для резервирования; Redis не является источником истины для остатков.
Платежи
- В первой версии — один платёжный провайдер и одна валюта.
- Провайдер и валюта должны быть выбраны до начала интеграции реальных платежей.
- Поддерживаются создание платёжной сессии, проверка webhook-подписи и сохранение статуса платежа.
- Идентификатор события провайдера уникален в БД для защиты от повторной обработки.
- Проверяются сумма, валюта, заказ и соответствие ожидаемому получателю/мерчанту, если это предусмотрено API провайдера.
- Секреты провайдера хранятся в переменных окружения, не в исходном коде.
- До выбора провайдера сценарий оплаты разрабатывается через mock/sandbox-интеграцию.
Личный кабинет
- Список заказов текущего пользователя.
- Статус заказа и информация о дате оформления.
- Получение содержимого купленного цифрового экземпляра только владельцем заказа.
- Значения цифрового товара не включаются в общие логи и не выдаются через публичный endpoint.
Администрирование
- Отдельный защищённый доступ; публичной регистрации администраторов нет.
- Создание/редактирование/архивация товара.
- Добавление цифровых экземпляров и просмотр остатков по статусам.
- Поиск заказа по ID и просмотр состояния оплаты/выдачи.
- Критические административные действия фиксируются в журнале.
- Создание или редактирование товара и запасов валидируется на backend.
Уведомления
- После успешной оплаты система планирует уведомление пользователю в Telegram, если доступен бот и пользователь может получить сообщение.
- Сбой отправки уведомления не отменяет заказ и не приводит к повторной продаже.
- Повторные попытки отправки должны быть безопасными и ограниченными.
5. Нефункциональные требования
Целостность данных
- Один digital_item может быть связан не более чем с одной завершённой продажей.
- Критические изменения заказа, резерва и экземпляра выполняются транзакционно.
- База данных обеспечивает уникальность ID событий webhook и ключей идемпотентности в соответствующих областях действия.
- Нельзя считать успех оплаты на основании redirect/callback браузера; нужен проверенный webhook или подтверждение через API провайдера.
Безопасность
- Проверка прав доступа на каждом endpoint; пользователь не может посмотреть заказы или ключи другого пользователя.
- Валидация входных данных через Pydantic.
- Rate limiting для чувствительных публичных endpoint.
- CORS, cookie/session-настройки и HTTPS определяются для целевого окружения.
- Ключи и другие цифровые секреты защищаются при хранении; способ шифрования и управление ключом фиксируются до загрузки реальных товаров.
- .env не коммитится; .env.example содержит только названия переменных и безопасные примерные значения.
- Не логировать токен Telegram, платёжные секреты, полные webhook-секреты или содержимое цифровых товаров.
Сопровождение
- Логи с correlation/request ID для расследования ошибок.
- Endpoint liveness/readiness для проверки состояния приложения.
- Миграции схемы через Alembic.
- Тесты критических сценариев, включая конкурентные запросы.
- Документированные команды локального запуска и тестирования.
Производительность
- Для MVP не обещается конкретный промышленный RPS без замеров.
- Каталог использует пагинацию и индексы по реально используемым фильтрам.
- Отдельные нагрузочные тесты проверяют сценарий конкуренции за последний экземпляр.
6. Предлагаемый стек
- Backend: Python 3.11+, FastAPI, SQLAlchemy Async, Pydantic v2.
- Основная БД: PostgreSQL.
- Redis: rate limiting, кэширование и/или координация фоновых задач; не источник истины для склада.
- Миграции: Alembic.
- Frontend: React, TypeScript, Vite, Telegram Web Apps SDK; TailwindCSS при необходимости.
- Инфраструктура локальной разработки: Docker Compose.
- Nginx и HTTPS-конфигурация добавляются для развёртывания в публичной среде.
- Тесты backend: pytest и интеграционные тесты с PostgreSQL.
7. Основные сущности данных
Минимальный набор таблиц:
- users — пользователь Telegram, статус, даты создания.
- products — описание, категория, цена, валюта, публикация, даты.
- digital_items — экземпляр цифрового товара, статус, защищённое содержимое, временные метки.
- orders — пользователь, сумма, валюта, состояние, время резерва, idempotency key.
- order_items — связь заказа с товаром, количество и цена на момент покупки; при продаже уникального экземпляра связь с digital_item должна быть защищена ограничениями БД.
- payments — провайдер, внешний ID, сумма, валюта, состояние и привязка к заказу.
- payment_events — внешние ID webhook-событий и результат обработки; внешний ID события уникален в пределах провайдера.
- outbox_events или эквивалентная таблица задач — надёжная постановка уведомлений/фоновых событий, если используется outbox-паттерн.
- admin_audit_logs — критические действия администраторов.
Названия и точные связи фиксируются на этапе проектирования модели данных; схема должна сохранять историю заказов после архивации товара.
8. Границы MVP
В MVP сознательно не обещаем:
- 100% доступность или гарантированный RPS до нагрузочных испытаний.
- Поддержку десятков платёжных провайдеров.
- Автоматизированные выплаты множеству продавцов.
- Глобальную распределённую архитектуру, несколько регионов и сложное шардирование.
- Продажу товаров, для которых нет права на распространение, а также незаконно полученных или скомпрометированных аккаунтов.
9. Дорожная карта
Оценки ориентировочные для одного разработчика, который уже знаком со стеком. При параллельном освоении технологий срок может заметно увеличиться.

Этап 4 — заказ, резервирование и склад
Оценка: 4–7 дней.
- Реализовать состояния заказа и цифрового экземпляра.
- Создавать заказ с зафиксированной ценой и ключом идемпотентности.
- Резервировать экземпляр в короткой транзакции с блокировкой PostgreSQL.
- Освобождать истёкшие резервы фоновой задачей.
- Добавить обработку отказов и конфликтных переходов статуса.
Готово, когда: конкурентный тест на последний экземпляр не допускает двойного резервирования/продажи; повтор создания заказа с тем же ключом не создаёт дубликат.
Этап 5 — платёжная интеграция
Оценка: 3–6 дней, зависит от провайдера.
- Сначала реализовать mock/sandbox провайдера.
- После выбора провайдера подключить создание платёжной сессии.
- Реализовать проверку подписи webhook, суммы, валюты и заказа.
- Добавить идемпотентную обработку событий и сценарий поздней оплаты.
Готово, когда: поддельный webhook отклоняется; повторное событие не дублирует оплату/выдачу; сумма и валюта сверяются с заказом.
Этап 6 — интерфейс покупки и личный кабинет
Оценка: 4–7 дней.
- Каталог, карточка товара, состояние загрузки и ошибки.
- Кнопка покупки, экран статуса оплаты и результата заказа.
- История заказов.
- Защищённый просмотр купленного цифрового товара и действие копирования.
- Адаптация к теме и viewport Telegram Mini App.
Готово, когда: тестовый пользователь проходит весь сценарий без ручного изменения БД.
Этап 7 — уведомления, тестирование и документация
Оценка: 3–5 дней.
- Повторяемая отправка Telegram-уведомлений без повторной выдачи.
- Тесты для авторизации, прав доступа, заказов, webhook и истечения резерва.
- Конкурентный тест последнего экземпляра.
- Обработка ошибок, логирование и обновление README.
Готово, когда: критические сценарии автоматически проверяются; локальный запуск воспроизводим по инструкции.
Этап 8 — тестовый деплой (отдельно от локального MVP)
Оценка: 1–3 дня после выбора хостинга.
- Конфигурация окружения, HTTPS и домена.
- Миграции при развёртывании.
- Резервное копирование PostgreSQL и проверка восстановления.
- Проверка логов, доступности и защиты секретов.
Ориентир по времени: около 4–8 недель для разработчика, уверенно владеющего стеком; ориентировочно 6–10+ недель, если технологии осваиваются параллельно. Реальные сроки уточняются после этапа 0.
10. Критерии приёмки MVP
MVP можно считать функционально готовым к закрытому тестированию, если:
1. Пользователь может открыть Mini App и пройти проверку Telegram-авторизации.
2. Каталог получает опубликованные товары из API и показывает цену/наличие.
3. Администратор может создать товар и загрузить цифровые экземпляры.
4. Пользователь может создать заказ; цена берётся из базы, а не из запроса клиента.
5. Одновременно конкурирующие запросы не могут продать один цифровой экземпляр дважды.
6. Повтор запроса создания заказа и повтор webhook не приводят к повторному заказу, списанию или выдаче.
7. Недействительный webhook и несовпадающая сумма/валюта отклоняются или отправляются на безопасную проверку.
8. Истёкший резерв освобождается; поздняя оплата обрабатывается безопасно без выдачи уже проданного экземпляра.
9. Пользователь видит только собственные заказы и собственные купленные товары.
10. Сбой отправки Telegram-сообщения не отменяет покупку.
11. Проект запускается локально по документации, миграции применяются воспроизводимо, основные тесты проходят.
